# Example: Vertical Slice Decomposition — Shop VAT/Tax Feature

This is a worked example showing how `to-issues` decomposes a PRD into
tracer-bullet vertical slices. Project: Shop (e-commerce, Express/Prisma/Vitest).

## Source PRD

PRD: "VAT & Tax Calculation" — shop must calculate correct VAT rates per
customer country, display tax-inclusive prices, store VAT metadata on orders,
and generate tax-compliant invoices.

> This PRD would normally be generated by `to-prd` from the planner's context.

### User Stories (excerpt from PRD)

1. As a EU customer, I want to see prices with my local VAT rate included,
   so that I know the final price I'll pay.
2. As a UK customer, I want 20% VAT applied correctly post-Brexit,
   so that I pay the right tax.
3. As a US customer, I want to see prices without VAT at checkout,
   but have my state sales tax calculated based on my shipping address.
4. As an admin, I want to review VAT metadata on orders,
   so that I can file quarterly tax returns.
5. As an admin, I want invoices to show VAT breakdowns,
   so that business customers can reclaim VAT.

## Vertical Slice Decomposition (output of `to-issues`)

### Slice 1: VAT Rate Lookup (AFK)

**What to build:** A VAT rate lookup service that maps country codes to VAT rates.
Supports standard EU rates, UK, and a mechanism for country exceptions.
Returns the applicable rate for a given country. No UI changes yet —
just the backend data + unit tests.

**Layers traversed:** DB (VAT rates table) → Service (rate lookup) → Tests (unit)

- **Type:** AFK
- **Blocked by:** None - can start immediately
- **User stories:** Supports #1, #2

```
## Parent
PRD: Shop VAT & Tax Calculation

## What to build

Create a VAT rate lookup service (app/services/vat.server.ts) backed by a
database table of country→rate mappings. The service must:
- Return the standard VAT rate for any EU member state (stored in DB)
- Return the UK rate (20%, post-Brexit)
- Return 0% for non-VAT countries (US, etc.)
- Be cacheable — rates change infrequently

The DB table should be seeded with current EU + UK rates. US states are
not in scope for this slice (state-level sales tax is Slice 3).

## Acceptance criteria

- [ ] `getVatRate('FR')` returns 0.20 (decimal)
- [ ] `getVatRate('GB')` returns 0.20 (decimal)
- [ ] `getVatRate('US')` returns 0 (decimal)
- [ ] `getVatRate('XX')` returns 0 for unknown countries (safe default)
- [ ] All EU-27 countries are seeded with correct rates
- [ ] Service is unit-tested with vitest

## Blocked by

- None - can start immediately
```

---

### Slice 2: Price Display with VAT (AFK)

**What to build:** Wire the VAT rate lookup into the product listing and cart
pages so that displayed prices reflect the customer's country. Prices already
stored as tax-exclusive in the DB get the correct VAT rate applied on display.
No invoice generation yet — just the price you see on the page.

**Layers traversed:** Service (VAT calc) → Route (pass country to template) →
View (display VAT-inclusive price) → E2E tests

- **Type:** AFK
- **Blocked by:** Slice 1 (VAT Rate Lookup)
- **User stories:** #1, #2

```
## Parent
PRD: Shop VAT & Tax Calculation

## What to build

Integrate the VAT rate lookup service (from Slice 1) into the product listing
and cart pages. When rendering prices:
1. Determine customer country from session/geolocation (default: FR)
2. Fetch VAT rate for that country
3. Display tax-inclusive price alongside base price

Add a small "(incl. VAT)" / "(excl. VAT)" label. The admin panel continues
showing tax-exclusive prices (no change needed).

## Acceptance criteria

- [ ] Product listing shows VAT-inclusive price for a French visitor (20%)
- [ ] Product listing shows VAT-inclusive price for a German visitor (19%)
- [ ] Cart shows VAT-inclusive subtotal
- [ ] US visitor sees only tax-exclusive price labeled "(excl. tax)"
- [ ] E2E test: Playwright visits as FR user, verifies price label
- [ ] E2E test: Playwright visits as US user, verifies no VAT label
- [ ] Admin panel prices are unchanged (always tax-exclusive)

## Blocked by

- Slice 1 (VAT Rate Lookup)
```

---

### Slice 3: Order VAT Metadata (AFK)

**What to build:** When an order is created, persist the VAT rate and calculated
VAT amount in the order record. This decouples the tax calculation from the
checkout moment — if rates change later, historical orders are unaffected.

**Layers traversed:** DB (schema change) → Service (calculation at order time) →
Route (order creation) → Tests (unit + e2e)

- **Type:** AFK
- **Blocked by:** Slice 1 (VAT Rate Lookup)
- **User stories:** #4

```
## Parent
PRD: Shop VAT & Tax Calculation

## What to build

Add `vatRate`, `vatAmount`, and `vatCountry` fields to the Order model (Prisma
schema). When an order is created:
1. Look up the VAT rate for the customer's country (from Slice 1)
2. Calculate the VAT amount: subtotal × vatRate
3. Store both alongside the order

This is a DB + backend change. No UI change in this slice — the admin order
detail page update comes in Slice 5.

## Acceptance criteria

- [ ] Order table has vatRate (Decimal), vatAmount (Decimal), vatCountry (String)
- [ ] Creating an order for a French customer stores vatRate=0.20, vatAmount=subtotal*0.20
- [ ] Creating an order for a US customer stores vatRate=0, vatAmount=0
- [ ] Existing orders are unaffected (nullable columns, default NULL)
- [ ] Unit test: order service calculates VAT correctly
- [ ] E2E test: full checkout flow stores VAT on the order

## Blocked by

- Slice 1 (VAT Rate Lookup)
```

---

### Slice 4: Invoice VAT Breakdown (AFK)

**What to build:** The invoice PDF (already exists as a feature) now includes a
VAT breakdown section sourced from the order's VAT metadata. Shows: subtotal,
VAT rate, VAT amount, total.

**Layers traversed:** Service (read order VAT) → PDF template (render breakdown) →
Route (invoice endpoint) → E2E tests

- **Type:** AFK
- **Blocked by:** Slice 3 (Order VAT Metadata)
- **User stories:** #5

```
## Parent
PRD: Shop VAT & Tax Calculation

## What to build

Update the invoice PDF generator to include a VAT breakdown section when the
order has VAT metadata (vatRate > 0). The breakdown shows:
- Subtotal (tax-exclusive)
- VAT rate (e.g., "20% (France)")
- VAT amount
- Total (tax-inclusive)

For orders with vatRate=0 (US customers), omit the VAT section entirely.
The invoice should still render correctly for pre-existing orders that have
NULL VAT fields (no retroactive changes).

## Acceptance criteria

- [ ] Invoice for a French order shows VAT breakdown with 20% rate
- [ ] Invoice for a UK order shows VAT breakdown with 20% rate, labeled "UK"
- [ ] Invoice for a US order shows no VAT section
- [ ] Invoice for an old order (NULL VAT fields) renders without error
- [ ] E2E test: create order, generate invoice, verify PDF contains VAT line
- [ ] VAT amounts match Slice 3's stored values

## Blocked by

- Slice 3 (Order VAT Metadata)
```

---

### Slice 5: US State Sales Tax (HITL)

**What to build:** Add state-level sales tax for US customers. This is more
complex than VAT because it varies by state AND by product category.
Needs architectural decision on third-party API vs local table.

**Layers traversed:** Research (API evaluation) → Architecture decision →
Service → DB → Tests

- **Type:** HITL
- **Blocked by:** Slice 1 (VAT Rate Lookup)
- **User stories:** #3

```
## Parent
PRD: Shop VAT & Tax Calculation

## What to build

Add US state-level sales tax calculation. This requires a decision:
- Option A: Integrate a third-party tax API (TaxJar, Avalara) — accurate but
  adds an external dependency + recurring cost
- Option B: Maintain a local table of state rates with product category
  exemptions — simpler but requires quarterly manual updates

The task is to: research both options, present a recommendation with cost
estimates, and get user approval BEFORE implementing. Implementation happens
only after the architectural decision is confirmed.

## Acceptance criteria

- [ ] Research document: API options, pricing, rate limits, coverage
- [ ] Research document: local-table approach, maintenance burden estimate
- [ ] Recommendation with trade-offs presented to user
- [ ] User decision documented as an ADR
- [ ] (Only after decision) Implementation per chosen approach

## Blocked by

- Slice 1 (VAT Rate Lookup)

## Notes

This is HITL because the architectural decision (API vs local table) has cost
implications and requires user judgment. The task should be created with
`--triage` or `--blocked` status until the decision is made.
```

---

## Dependency Graph

```
Slice 1 (VAT Rate Lookup) ──┬── Slice 2 (Price Display)
                            ├── Slice 3 (Order VAT Metadata) ── Slice 4 (Invoice Breakdown)
                            └── Slice 5 (US Sales Tax - HITL)
```

Slices 2, 3, and 5 can all start as soon as Slice 1 is done.
Slice 4 must wait for Slice 3.
Slice 5 is HITL — it blocks on a human decision, not on other tasks.

## What makes this "vertical slices" (not horizontal)

| Horizontal (WRONG) | Vertical (CORRECT) |
|---|---|
| "Build VAT DB schema" | Slice 1: Rate lookup (DB + service + tests) |
| "Add VAT to the API layer" | Slice 2: Price display (service + route + view + e2e) |
| "Generate VAT in PDFs" | Slice 4: Invoice breakdown (service + PDF template + route + e2e) |
| "US tax research" | Slice 5: Research + decision + implementation in one HITL slice |

Each vertical slice delivers a COMPLETE, VERIFIABLE behavior from DB through to
user-visible output. No slice is "just the database" or "just the UI."
